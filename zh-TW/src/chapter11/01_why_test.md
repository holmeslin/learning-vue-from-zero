# 為什麼要寫測試

## 本集目標

了解自動化測試解決什麼問題，以及這一章會測哪些東西。

## 正文

### 手動測試的問題

假設你寫了一個函式，算購物車的折扣：滿 3000 元打九折。

```ts
export function applyDiscount(total: number): number {
  return total > 3000 ? total * 0.9 : total;
}
```

你試了 5000 元，得到 4500，沒問題；試了 1000 元，得到 1000，也沒問題。你覺得寫好了。

但規格是「**滿** 3000 元」，剛好 3000 元也要打折。上面寫的是 `>`，不是 `>=`，剛好 3000 元的客人會多付 300 元。這種「剛好在邊界上」的錯誤，手動測試很難想到。

更麻煩的是，就算今天你測過了，下週有人改了這個函式、或改了它附近的程式，你還會記得重新測剛好 3000 元嗎？

### 自動化測試

自動化測試是把檢查的過程寫成程式：

```ts
expect(applyDiscount(3000)).toBe(2700);
```

這一行的意思是：「`applyDiscount(3000)` 的結果應該是 2700」。寫一次之後，每次改了程式，執行一個指令，所有的測試就全部重跑。哪裡壞了，馬上知道是哪一個。

這帶來幾個好處：

- **改程式有底氣**：重構、升級套件、修 bug 之後，跑一下測試就知道有沒有弄壞別的地方。
- **測試本身是說明書**：看測試就知道這個函式「應該」怎麼運作，包括邊界的情況。
- **越早抓到 bug 越便宜**：寫的當下就發現，比上線後被使用者發現好處理太多。

### 要測什麼

不是所有東西都要測。測試也要花時間寫、花時間維護。優先測這些：

1. **有邏輯的函式**：計算、轉換、驗證，像折扣、金額、表單檢查。它們輸入和輸出很明確，最好測。
2. **使用者看得到、做得到的行為**：按下按鈕畫面會變、輸入東西會顯示、載入失敗會有錯誤訊息、送出表單會發出事件。
3. **曾經出過 bug 的地方**：修好之後補一個測試，保證同樣的 bug 不會再出現。

不需要測的是：Vue 本身（Vue 已經有人測過了）、單純排版的樣式、第三方套件內部的運作。

### 這一章的做法

這一章從最簡單的測試一路往上，每一集加一點：

1. 建立有 Vitest 的專案，看懂它產生的設定
2. 測純函式，學會 `describe`、`test`、`expect`
3. 用 `mount` 渲染元件，用 `find`、`get` 找元素
4. 用 `trigger`、`setValue` 模擬點按鈕和打字
5. 測 props 與 emit
6. 測非同步的行為
7. 用假的東西取代真的（`vi.fn`、`vi.mock`）
8. 測 composable 和 Pinia store

先從建立專案開始。

## 重點整理

- 手動測試很難涵蓋邊界情況，也很難在每次修改後重複。
- 自動化測試把檢查寫成程式，一個指令就能全部重跑。
- 優先測有邏輯的函式、使用者看得到的行為，以及曾經出過 bug 的地方。
- 這一章用 Vitest 執行測試，用 Vue Test Utils 掛載元件和模擬操作。
